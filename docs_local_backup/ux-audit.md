# ITLW UX audit

**Scope:** source and documentation review of the launch dashboard, transformer workbench, controls, hardware status, updater, and app lifecycle. The Pygame screens were rendered headlessly at their reference sizes with `ITLW_HARDWARE=0`. This confirms layout composition only; no Wayland display, physical controls, systemd service, or real update flow was exercised.

## 1. Summary

**The first screen does not lead into a working demonstration.** The app opens on the dashboard, but its “Demo Tutorial” is a placeholder containing only three terse instructions. The workbench then starts at `Vp = 0`, `Np = 0`, and `Ns = 0`, with both turn dials disabled until a mode is selected. Reset returns to the same state. A learner must infer the order of operations and build a valid example from zero before seeing a useful result.

**Help and shortcut behavior disagree with the interface and README.** The workbench’s `H` key returns Home instead of showing help; `A` toggles a state that is not used by rendering; `M` toggles modes, while the README describes a help panel and animation toggle that do not exist. Tab focus gives no visible focus state for voltage and does not implement the documented reverse navigation. Learners cannot reliably discover keyboard controls or trust the shortcut guide.

**Hardware faults can both slow the interface and stay invisible.** ADS reads and retry sleeps run from the main loop. When the bus fails, the two channels can block the loop for roughly 200 ms per attempted sample, and failed samples are retried again on the next frame. Hardware initialization or GPIO errors also have no persistent on-screen explanation; the header only shows one specific ADC status, and only on the workbench.

**The visual layout is readable at its reference size but not truly responsive.** The workbench is drawn at 1240 × 544 and the dashboard at 1240 × 620, then each is stretched independently to fill the window. This changes aspect ratio, distorts circles and text, and can make controls too small on lower-resolution Pi displays. A fixed 1280 × 720 window is configured, but fullscreen uses the display’s actual size.

**Status and documentation leave learners guessing.** Offline update checks look like the ordinary “Check for updates” state, so there is no visible distinction between no update, no network, rate limiting, and a failed check. Hardware status is similarly partial. The README describes an older screen and input model, including help, keyboard behavior, defaults, button pins, and update branch behavior that do not match the current source.

There are only two actual screens: the launch dashboard and the workbench. There is no settings screen or help screen. Update confirmation and updating are overlays. Error/offline states are mostly implicit labels or logs rather than screens. Clean shutdown is by `Esc` or window close; the intended power menu is unreachable.

### Display and visual sizing

- Configured window: 1280 × 720; resizable minimum: 900 × 620. The Pi installer sets fullscreen.
- Dashboard reference surface: 1240 × 620. Workbench reference surface: 1240 × 544. `main.py` scales each surface to the full window independently instead of preserving its aspect ratio.
- Main values are large and high contrast. Supporting labels range down to 9–12 px on the reference surfaces; status and footer text is especially small.
- The headless render showed a sparse launch dashboard with large document/tutorial placeholders and a denser but legible workbench. It does not show how either surface reads on a particular Pi panel after stretching.

## 4. Quick wins

1. Set useful nonzero initial values and make Reset restore them; start in a valid Step-up example so the first frame demonstrates `Vs = Vp × (Ns / Np)`.
2. Correct the help/shortcut mismatch: either implement the advertised help and animation behavior or remove those shortcuts from config/docs; make `H` do one predictable thing.
3. Replace the dashboard tutorial placeholder with a short, ordered first task and a clear physical-control legend.
4. Show hardware status on the launch page and workbench, with separate wording for ADC, GPIO, and fully unavailable hardware.
5. Bring README instructions and hardware pin tables into line with current screens, defaults, shortcuts, and update behavior.
6. Show a distinct “Couldn’t check GitHub” state and last-check time rather than returning silently to “Check for updates.”
7. Remove or wire up the currently unreachable power menu so the visible/reported exit behavior is accurate.

## 5. Validation notes

- Headless Pygame rendering succeeded for both reference surfaces with hardware disabled: dashboard 1240 × 620 and workbench 1240 × 544.
- This audit did not test the app on the Raspberry Pi panel, with physical GPIO/ADC inputs, under real I2C faults, or through systemd restart/shutdown flows.
- I did not run the event loop interactively or exercise an actual GitHub update. The workspace already had updater-related local edits from earlier work; this audit did not modify those files.
